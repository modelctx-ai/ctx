# ADR 0007：会话的擦除和保留期

- 状态：已采纳
- 实施状态：会话这一半已实施，未发布。记忆那一半（`forget` 级联到画像、画像历史、笔记和向量，「按会话或按用户全部删除」的入口）不在这篇里，已经单独实施，未发布：`Memory.forget`，见 [ADR 0006](0006-memory.md#决定记录) 2026-11-16 的一条
- 日期：2026-11-15
- 范围：`ctx-protocol`（`SessionStore`）、`@modelctx-ai/ctx`（内存存储、harness、`pruneSession`）、`ctx-sqlite`、`ctx-remote`
- 依据：issue #36、#32、#38；在 Node 22.23 自带的 SQLite 3.53.4 上实测

## 背景

[ADR 0003](0003-context-model.md) 定的是只追加：条目写进去就不改，除了 `clear(session)` 没有删除，它的「代价」一节也写了「存储空间一直增长」「改不了过去」。三件事让这条站不住：

1. **用户要求删除。** 用户说了不该留的内容（卡号、别人的隐私），应用只能把整个会话清掉。
2. **被摘要盖住的历史永远留着。** 压缩之后投影不再读它们，但没有办法删，库只增不减。
3. **`clear` 不是真擦除。** #36 实测：`ctx-sqlite` 写 200 条带标记的消息，`clear`、`wal_checkpoint(TRUNCATE)`、关库之后，库文件里还能找到 206 处标记，文件也没变小（`secure_delete` 和 `auto_vacuum` 都是 0）。

另外两条约束来自别的 issue：#32 要求删除让运行中的 harness 看得见（当时的现象是 `clear` 之后这一轮的收尾把会话写了回来，已经修了 `clear` 这一种）；#38 要求读不了的坏行能按 `id` 修复或删除，和这里的按 `id` 删除用同一个接口。

## 决定

### 1. `SessionStore` 加三个必选方法

```ts
truncate(session: string, upTo: number): Promise<number>; // 删掉 seq ≤ upTo 的
remove(session: string, ids: readonly string[]): Promise<number>; // 按 id 真删
redact(session: string, ids: readonly string[]): Promise<number>; // 按 id 涂改，位置留着
```

都返回真正动了的条数；认不得的、别的会话的 `id` 跳过，不算错。只按列操作、不解码正文，所以读不了的行也删得掉、涂得掉（#38）。三个都是必选：删除是用户的权利，不该取决于换了哪个存储。

`redact` 把条目换成一条 `ctx.redacted` 事件：`id`、`session`、`seq`、`at`、`key`、`source` 留着，消息、文字、数据、`meta` 去掉，`data` 只记原来的类型和消息的角色。留位置是为了 `covers`、记忆的证据区间照常指得到；留 `key` 是为了同一个幂等键的重试不会把内容写回来。`remove` 之后 `id` 和 `key` 让出来，和 `clear` 一样。

### 2. 擦除留一条记录，末尾一定往前走

三个操作真的动了条目时，存储在同一次原子操作里追加一条 `ctx.erased`（`{ op, upTo?, seqs?, count }`，`source: 'store'`）。只有位置，没有内容。什么都没动就不追加。

这一条同时解决四件事：

- **`expectSeq`。** 末尾一定前进一格，拿着旧末尾的写入一定 `conflict` 一次，重读就看得到记录。没有这条记录的话，`truncate` 不动末尾（没人知道），`remove` 掉最后一条会让末尾回退（旧的 `expectSeq` 反而又对上了）。
- **`seq`。** 不回退、不复用，哪怕删到末尾：记录的 `seq` 比删掉的都大。
- **`watch` 和镜像。** 订阅方收得到记录，照着它改自己手里的副本。
- **审计。** 日志里看得出什么时候删过哪些位置。

`clear` 不变：会话回到空，末尾回到 0，不留记录，`sessions` 不再列它。要留痕迹的「清空」是 `truncate(session, 末尾)`。

### 3. 运行中的 harness：自己写的条目被擦除就停下

harness 的每次写入带 `expectSeq`，擦除之后必然冲突一次。冲突时它本来就读自己的 `ctx.run.started` 起的生命周期事件，现在一起读 `ctx.erased`：

- 自己的 `ctx.run.started` 不在了（`clear`，或者 `truncate`、`remove` 删到了它）；
- 或者有擦除记录动了这一轮自己写的条目（输入、产出，`redact` 也算）；

就是被围栏，以 `aborted` 停下，不再写产出和 `ctx.run.ended`。删的是这一轮之前的历史、或者别人在这期间写的应用事件，就只是换个末尾接着写。

规则按「这一轮写的条目」定，不按「这一轮期间的任何条目」：应用常在运行期间写了又删自己的事件，不该因此杀掉一轮。

挡不住的：这一轮的上下文已经建好，模型仍然看得到被删的更早的内容，回复里可能再提到。要一并挡住就先取消这一轮再删。

### 4. 摘要不跟着改

摘要的文字是从被盖住的条目算出来的。`truncate`、`remove`、`redact` 都不碰摘要，被删的内容可能还在摘要里；要一起清就把摘要也 `redact`（它不再是摘要，被它盖住、还在的条目重新可见）再重新压缩。记忆里从这些条目提取的事实同理，归记忆那一半管。

### 5. SQLite：连接上开 `secure_delete`，给 `vacuum()`

- `createSqliteStore` 在连接上设 `PRAGMA secure_delete = ON`（新选项 `secureDelete`，缺省 `true`），应用传进来的 `database` 也设。这个开关是连接上的，不存进库文件，所以每次打开都设。
- 新方法 `vacuum()`：`VACUUM` 加 `wal_checkpoint(TRUNCATE)`。删除不会让文件变小，要空间、或者要清掉没开 `secure_delete` 时留下的内容，就调它。不自动调：它要独占库、重写整个文件。
- 不动 `auto_vacuum`：它只能在建表之前设，对已有的库没用，还要再 `VACUUM` 一次才生效。

「整条连接都开」而不是「只在删的时候开」，是实测出来的。先试的是后者（不动应用的连接设置，删除时临时打开、做完恢复）：在应用传进来的连接上写 200 条带标记的消息，再 `redact`、`remove`、`truncate`、`clear`、checkpoint、关库，库文件里仍然找得到标记。再用一张结构相近的表（自增主键、唯一的 `id`、一个二级索引；200 行，每行正文和 `meta` 各一处标记，分「都是短行」和「有几行长到用溢出页」两组）单独量：

| 写入时 `secure_delete` | 删除时 | 写完时文件里的标记 | 删除、checkpoint、关库之后                                  |
| ---------------------- | ------ | ------------------ | ----------------------------------------------------------- |
| 开                     | 开     | 400、404           | 0                                                           |
| 关                     | 开     | 553、485           | `DELETE` 之后剩 2、53；`UPDATE`（涂改的做法）之后剩 153、81 |

写入时没开的话，写完时标记就比行里的多：页分裂在页内留下了行内容的旧副本。这些副本不属于任何一行，之后开着删也擦不到。在不在事务里做，结果一样。所以写入也要开着；升级之前写进去的内容只有 `vacuum()` 清得掉。这是 SQLite 内部的行为，没有文档保证，换版本可能不同；测试只断言「开着写、开着删之后找不到」和「`vacuum()` 之后找不到」。

### 6. 保留期是应用调的函数

`pruneSession(store, session, { keep?, maxAgeMs? })` 放在 `@modelctx-ai/ctx`：删掉被生效的摘要盖住的历史，按条数或时间留一部分，走 `truncate`。没有定时器，什么时候调由应用定（[概念](../concepts.md)的约束 5）。它只读 `list`、只调 `truncate`，对任何存储都能用；不放协议包，因为它是策略不是协议形状，和 `findLossySummaries` 同一个位置。

两条保守的规则：会话里有未结束的运行时不删到它的 `ctx.run.started`（删到了那一轮会被围栏）；按时间删时只删开头连续过期的一段（补写的旧记录 `at` 早、`seq` 大，不会连累排在它前面的新条目）。

## 破坏面

| 谁             | 影响                                                                                                                                                                |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 自己实现的存储 | 不兼容：要实现三个方法并通过契约测试的新用例。内存里的存储可以直接用纯函数 `eraseEntries`                                                                           |
| 手写的假存储   | 列全了方法的对象字面量要补三个方法；`{ ...store, append }` 这种展开的不用改                                                                                         |
| `ctx-sqlite`   | 连接上多了 `secure_delete`（含应用传进来的连接）：删除和改写多写一些零，其余行为不变。不要的传 `secureDelete: false`。没有结构迁移，结构版本不变                    |
| `ctx-remote`   | 加三条 `POST` 路径；新客户端对旧服务端调这三个方法得到 404                                                                                                          |
| 读日志的代码   | 会话里可能出现 `ctx.erased`、`ctx.redacted` 两种事件，缺省不进模型上下文；按 `seq` 连续性做假设的代码本来就不该有（`seq` 不要求连续）                               |
| yoyo           | 不用改：它不手写完整的 `SessionStore`（只有一处 `{ ...store, append }`），运行全是 `record: false`，不受围栏规则影响。它的 `yoyo.db` 连接上会多一个 `secure_delete` |

## 代价

- 「只追加」多了例外，日志不再是不可变的：读到的历史可能比以前短，同一个 `seq` 的内容可能变成占位。依赖「原条目一直在」的地方（记忆的证据、`resultFromLog`）要接受证据可能已经不在。
- 每次擦除多一条记录，频繁清理的会话里会攒下一些 `ctx.erased`（下一次 `truncate` 会把更早的记录一起删掉）。
- 擦除让运行中的一轮多冲突一次；工具在这一轮里删这一轮自己的条目，这一轮会停下。
- `secure_delete` 让删除多一些写入；`vacuum()` 要独占库。
- 擦得掉的只是库文件里的内容：`-wal` 要等 checkpoint，摘要、记忆、备份、文件系统和存储介质上的残留都不在这个保证里。

## 没有采用

- **软删除（加一个 `deleted` 标记）。** 内容还在库里，不是删除；每个读的地方都要过滤。
- **擦除不留记录。** `truncate` 不动末尾时没有任何人知道发生过；`remove` 掉最后一条会让末尾回退，旧的 `expectSeq` 又对上。
- **`clear` 也留记录。** 清空之后会话不再是空的，`sessions`、`expectSeq: 0` 的现有语义都要改；要留痕迹用 `truncate(session, 末尾)`。
- **三个方法做成可选（`truncate?`）。** 调用方每处都要判断，删除能不能做取决于存储，对用户说不清。
- **一个方法加选项（`remove(ids, { redact })`）。** 两种操作对 `id`、`key`、位置的处理都不同，分开更清楚。
- **只在删除时临时打开 `secure_delete`。** 不动应用的连接设置，但实测擦不干净（见决定 5 的表）。
- **`auto_vacuum = INCREMENTAL`。** 只对新库有效，旧库要先 `VACUUM`；回收的时机还是要应用来定，不如直接给 `vacuum()`。
- **框架里的定时清理。** 什么时候删、留多少是应用的事。
- **harness 在每次写入前重读自己的条目。** 每次写入多一次读，远端存储上很贵；靠记录触发一次冲突就够了。
